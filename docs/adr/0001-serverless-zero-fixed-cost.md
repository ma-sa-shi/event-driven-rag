# ADR-0001: サーバーレス構成による固定費ゼロ方針

- Status: Accepted
- Date: 2026-07-18

## Context

本システムは社内向けRAGアプリである。稼働実績がないため利用量の実測値はなく、次の前提を置いて見積もる。利用者は招待制で登録した社内メンバー50人程度、1人あたりの利用頻度を週2回から3回とし、月あたり400件から600件のチャットを想定する。

この規模ではアイドル時間が支配的であり、常駐リソースを持つ構成では利用がない時間帯にも費用が発生し続ける。課題は、この少量利用に見合うコスト構造をどう実現するかである。

この前提は精度を要求しない。想定が一桁外れて月数千チャットになった場合も、従量課金の費用が比例して増えるだけで構成の見直しには至らないため、以降の判断は前提の誤差に影響されない。

## Decision

AWSのサーバーレスサービスのみで構成し、固定費が発生するリソースを原則として採用しない。

本ADRにおける固定費とは、利用の有無にかかわらず課金される専有リソースを指す。常駐する計算資源、確保済みの同時実行数、待機状態のインスタンスがこれにあたる。保存データ量に比例するストレージ課金は対象に含めない。

利用するのはLambda、DynamoDB、S3、S3 Vectors、SQS、CloudFront、Cognito、SSM Parameter Storeである。次のリソースは固定費が発生するため採用しない。

- VPCとNAT Gateway
- ECSとEC2
- Aurora
- Provisioned Concurrency

採用理由は、全サービスが従量課金のみで構成でき、アイドル時のインフラ費用をゼロにできるためである。

固定費が発生するリソースを採用する場合は、次の3点をADRに記録した上で例外として扱う。原則を却下側のデフォルトとし、採用する側に説明責任を課す。

- そのリソースによって得られる価値
- 月額費用の見積もり
- 従量課金の代替手段が存在しないこと

## Consequences

メリット

- 想定する月400件から600件のチャットではインフラ費用を約$1〜2/月に抑えられる
- 負荷に応じて自動的にスケールする
- パッチ適用や稼働監視の対象となる常駐リソースが存在しない

デメリット・制約

- Lambdaのコールドスタートによる初回応答の遅延を許容する必要がある
- VPC接続が前提のサービスを利用できず、データストアの選択肢がDynamoDBとS3系に限られる
- Lambdaの実行時間とペイロードサイズの上限を設計で回避する必要がある

見直し条件

- chat-fnの応答遅延が問題になった場合は、chat-fnに限りProvisioned Concurrencyの適用を検討する
- 利用量が想定を大きく超え、月数万チャット規模の常時利用となった場合は、常駐構成との費用比較をやり直す

## Alternatives

### ECS FargateやEC2による常駐構成

コールドスタートがなく、実行時間やペイロードの制約も緩い。しかし最小構成でもアイドル時間に費用が発生し、月数百チャットの利用量では費用が利用実態に見合わない。ネットワークやコンテナ基盤の運用負担も増えるため不採用とした。

### サーバーレス基本 + Provisioned Concurrencyの常時適用

コールドスタートを回避できるが、確保した同時実行数に対して常時課金が発生し、固定費ゼロの目的と矛盾する。遅延が実際に問題になってから適用を判断すれば十分であるため不採用とした。

### Aurora Serverless v2による最小構成

Aurora Serverless v2は最小容量を0 ACUまで縮退でき、アイドル時のコンピュート費用は発生しない。この点では固定費ゼロ方針と両立しうる。しかしAuroraはVPC内にしか配置できず、Lambdaから接続するにはVPC LambdaとNAT GatewayまたはVPCエンドポイントが必要となり、そこで固定費が発生する。加えて縮退状態からの復帰には数秒の遅延が伴う。本システムのアクセスパターンはRDBを必要とせず、DynamoDBで表現できるため不採用とした。
