# ADR-0001: サーバーレス構成による固定費回避方針

- Status: Accepted
- Date: 2026-07-18
- Updated: 2026-08-22

## Context

本システムは社内向けRAGアプリであり、現時点では稼働実績がないため利用量を予測できない。そのため、構成の選択は利用量そのものではなく、移植元のECS版と費用が逆転する損益分岐点を基準に判断する。損益分岐点は、下限の535時間/月を1チャット30秒として換算すると約64,000チャット/月である([コストモデルと損益分岐点](../cost-comparison.md))。本ADRは月間チャット数がこれを下回ると仮定する。

アイドル時間が支配的であり、常駐リソースを持つ構成では利用がない時間帯にも費用が発生し続ける。課題は、この利用量に見合うコスト構造をどう実現するかである。

## Decision

AWSのサーバーレスサービスのみで構成し、固定費が発生するリソースを原則として採用しない。

本ADRにおける固定費とは、利用の有無に関わらず課金される専有リソースを指す。常駐する計算資源や確保済みの同時実行数(Reserved Concurrency, Provisioned Concurrency)、待機状態のインスタンスがこれにあたる。一方、保存データ量に比例するストレージ課金は対象に含めない。

利用するのはLambda、DynamoDB、S3、S3 Vectors、SQS、CloudFront、Cognito、SSM Parameter Storeである。次のリソースは固定費が発生するため採用しない。

- VPCとNAT Gateway
- ECSとEC2
- Aurora
- Provisioned Concurrency

採用理由は、全サービスが従量課金のみで構成でき、アイドル時のインフラ費用をゼロにできるためである。

## Consequences

メリット

- 利用量が想定範囲にある限り、移植元構成よりインフラ費用を抑えられる
- 負荷に応じて自動的にスケールする
- パッチ適用や稼働監視の対象となる常駐リソースが存在しない

デメリット・制約

- Lambdaのコールドスタートによる初回応答の遅延を許容する必要がある
- 現在のAWS構成ではVPC接続が前提のサービスを利用できず、データストアの選択肢がDynamoDBとS3系に限られる
- Lambdaの実行時間とペイロードサイズの上限を設計で回避する必要がある

見直し条件

- chat-fnの応答遅延が問題になった場合は、chat-fnに限りProvisioned Concurrencyの適用を検討する
- chat-fnの月間実行回数が64,000件を超えた場合は、常駐構成との費用比較をやり直す。比較の手順と現時点の損益分岐点は[コストモデルと損益分岐点](../cost-comparison.md)に記録している

## Alternatives

### ECS FargateやEC2による常駐構成

コールドスタートがなく、実行時間やペイロードの制約も緩い。しかし最小構成でもアイドル時間に費用が発生し、損益分岐点を下回る利用量では費用が利用実態に見合わない。ネットワークやコンテナ基盤の運用負担も増えるため不採用とした。

### サーバーレス基本 + Provisioned Concurrencyの常時適用

コールドスタートを回避できるが、Provisioned Concurrencyに対して常時課金が発生し、固定費回避の方針と矛盾する。遅延が実際に問題になってから適用を判断すれば十分であるため不採用とした。

### Aurora Serverless v2による最小構成

Aurora Serverless v2は最小容量を0 ACUまで縮退でき、アイドル時のコンピュート費用は発生しない。この点では固定費回避方針と両立する。しかしAuroraはVPC内に配置する必要があり、Lambdaから接続するためのネットワーク構成にも追加コストと運用上の複雑さが生じる。加えて縮退状態からの復帰には数秒の遅延が伴う。本システムのアクセスパターンはRDBを必要とせず、DynamoDBで表現できるため不採用とした。
