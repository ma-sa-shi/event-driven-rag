# ADR-0012: チャットのSSEをPOSTとAuthorizationヘッダーで配信する

- Status: Accepted
- Date: 2026-08-06

## Context

chat-fnは質問を受け取り、LangGraphのnodeごとのstate更新をSSEで配信する。このストリームをブラウザからどう受け取るかが課題である。

ブラウザ標準のEventSourceはGETのみを扱い、リクエストヘッダーを設定できない。一方でADR-0004により、バックエンドはJWT検証のみを担い、認証はAuthorizationヘッダーのBearerトークンで受け取ると定めている。EventSourceを使うのであれば、トークンの渡し方かバックエンドの責務範囲か、どちらかの前提を崩す必要がある。

質問は最大2000文字を受け付ける。日本語はUTF-8で1文字3バイトであり、パーセントエンコードすると9バイトへ膨らむ。クエリ文字列で送る場合、最長の質問はURLだけで18KB近くに達する。

## Decision

`POST /api/chats/stream`で質問をリクエストボディとして送り、アクセストークンをAuthorizationヘッダーへ載せる。クライアントはEventSourceを使わず、fetchのレスポンスボディを読み進めてSSEを自前で解析する。

採用理由は次の3点である。

- アクセストークンがURLに現れない。アクセスログや障害調査で共有する記録へ平文で残る経路を持たない
- ADR-0004で定めた責務の範囲に収まる。バックエンドはJWT検証のみを担い、セッションとCSRF対策を持たない
- 認証方式が他のRESTエンドポイントと同一になり、バックエンドの検証処理を分けずに済む

## Consequences

メリット

- トークンの露出経路が、ADR-0010で受容した範囲を超えない
- 質問の長さがURLの制限を受けない
- SSEを配信するエンドポイントを、他のAPIと同じ認証・ルーティングの枠組みで扱える

デメリット・制約

- EventSourceの自動再接続と、Last-Event-IDによる再開を利用できない。ストリームが切れた場合は失敗として扱い、利用者が質問を送り直す
- [ADR-0011](./0011-api-gateway-migration.md)のとおり、統合タイムアウトの引き上げが反映されるまでストリームは29秒で打ち切られる。Self-RAGの実行時間はこれを超えうるため、切断は例外的な事象ではない
- SSEの解析と、Authorizationヘッダーの付与をクライアントで実装する。fetchで呼ぶためaxiosのインターセプタを共有できず、イベントの境界とマルチバイト文字がチャンク境界で分割される場合も自前で扱う

ただし、再接続を放棄する代償は本システムでは限定的である。

- グラフはcheckpointerを持たず、中断した位置から再開できない。再接続してもグラフ全体が再実行され、LLMとRerankの呼び出しが再度課金される
- 永続化はdoneイベントの直前にまとめて行う。ストリームが切れた場合DynamoDBには何も残らないため、質問を送り直すことが唯一の復旧手段になる

見直し条件

- 途中再開を実装する場合は見直す。checkpointerの導入と、Last-Event-IDを受け付ける仕組みが前提になる

## Alternatives

### EventSourceとクエリ文字列によるトークン受け渡し

EventSourceを使い、アクセストークンと質問をクエリ文字列で送る案である。クライアントの実装量が小さい。自動再接続も備えるが、checkpointerを持たない本システムでは再接続がグラフ全体の再実行にしかならず、利点として働かない。

しかしトークンがURLに含まれる。CloudFrontとAPI Gatewayのアクセスログは現時点で有効化していないものの、障害調査のために後から有効化しうるものであり、有効化した時点から正常系のすべてのリクエストがトークンごと平文で記録される。XSSを前提とするlocalStorageからの窃取とは発生条件が異なり、ADR-0010で受容した範囲を超えるため不採用とした。

質問をクエリ文字列へ載せる制約も残る。最長の質問では前述のとおりURLが18KB近くに達し、CloudFrontのURL長のクォータ8192バイトを超える。

### EventSourceとCookie認証

EventSourceはCookieを自動送信するため、トークンをURLへ載せずに済む。

しかしCookieの発行とCSRF対策をバックエンドが持つことになり、バックエンドはJWT検証のみを担うというADR-0004の範囲を広げる。SSEの1エンドポイントのために認証方式を二重化することにもなるため不採用とした。

### SSE解析ライブラリの導入

fetchでSSEを扱うライブラリを導入する案である。再接続やリトライを含む実装を任せられる。

しかし本システムが受け取るイベントは3種類に固定されており、再接続も上記のとおり利用しない。解析処理は60行程度に収まり、依存を1つ増やすほどの規模ではないため不採用とした。将来イベント種別が増えるか再接続が必要になった場合は再検討する。
