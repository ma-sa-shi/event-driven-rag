# ADR-0015: ドキュメントを物理削除し、ベクトルはキーの再構成で消す

- Status: Accepted
- Date: 2026-08-28

## Context

ドキュメントの取込を誤って実行したり、更新が必要となったドキュメントを削除する手段がなく、削除したくてもDynamoDBのレコード、S3の原本、S3 Vectorsのベクトルが現状残り続ける。

削除方式を決めるうえで、S3 Vectorsの制約がある。`DeleteVectors`はキー指定のみで、Metadataによる条件削除には対応しない。`ListVectors`にもフィルタがなく、`QueryVectors`はクエリベクトルが必要なため、`documentId`から削除対象を特定する用途には使えない。

また、フィルタ不可のMetadataはインデックス作成後に変更できない。そのため、後から削除フラグを追加するには全ベクトルの再登録が必要になる。

## Decision

ドキュメントは物理削除する。削除対象は本人のドキュメントに限り、以下の順序で削除する。

1. S3 Vectorsのベクトル
2. S3の原本
3. DynamoDBのレコード

ベクトルのキーは登録時の規約である`<documentId>#<チャンク番号>`から再構成する。必要なチャンク数はDynamoDBの`chunkCount`から取得する。

この方式を成立させるため、`chunkCount >= 登録済みベクトル数`を不変条件とする。ingest-fnは`PutVectors`より先に`chunkCount`を更新する。これにより、ベクトル登録後に取込が失敗しても、削除時に必要なキーを再構成できる。

DynamoDBのレコードは最後に削除する。途中で失敗してもレコードが残るため、ユーザーによる再実行で削除を継続できる。S3 VectorsとS3の削除は対象が存在しなくてもエラーにならないため、再実行は冪等である。

取込中のドキュメントは削除を拒否する。取込中に削除すると、ingest-fnが後からベクトルを登録し、DynamoDBのレコードを持たないベクトルが残るためである。DynamoDBの条件付き削除にも同じ条件を適用し、所有者確認から削除までの間に取込が開始される競合も防ぐ。

## Consequences

メリット

- 削除したドキュメントの本文がS3とS3 Vectorsから消える
- 検索対象から即座に外れる
- 削除が冪等で、途中で失敗しても再実行で回復できる

デメリット・制約

- 物理削除のため誤削除を復旧できない。Documentsバケットはバージョニングを有効にしておらず、DynamoDBのPITRもテーブル単位の復元しか提供しない
- チャット履歴が保持する検索チャンクの本文は削除対象外であり、過去のチャットからは引き続き参照できる
- `chunkCount`が登録済みベクトル数を下回ると消し残しが発生する。この不変条件はingest-fnの実装上の制約となる

見直し条件

- 誤削除からの復旧が必要になった場合は、論理削除を導入する前にDocumentsバケットのバージョニングと旧バージョンの自動失効を検討する
- S3 VectorsがMetadataによる条件削除に対応した場合は、`chunkCount`に依存しない削除方式を検討する

## Alternatives

### 論理削除

削除フラグを立て、レコードと原本を残す方式。

復旧できる利点はあるが、検索からの除外が難しい。ベクトルに削除フラグを追加するには全ベクトルの再登録が必要であり、検索後にchat-fnで除外すると上位k件を削除済みチャンクが占め、検索品質が低下する。

今回の削除要求は主に誤ってアップロードしたファイルの取り消しであり、復旧性よりも内容を残さないことを優先する。

### 全件走査によるベクトルの特定

`ListVectors`でインデックス全体を走査し、Metadataの`documentId`が一致するベクトルを削除する方式。

`chunkCount`に依存しない利点はあるが、1件の削除でインデックス全体の読み出しが必要になる。保存量に比例してリクエスト数と所要時間が増加し、api-fnのタイムアウトにも収まらなくなるため採用しない。
