# ADR-0002: SPAの静的配信を採用、SSR不採用

- Status: Accepted
- Date: 2026-07-18

## Context

フロントエンドの配信・実行方式として、静的配信のSPAとSSRが候補となる。本システムは社内向けアプリであり、検索エンジン最適化や初期表示性能への強い要求はない。課題は、要件に対して過剰にならない配信方式を選ぶことである。

## Decision

Vite + ReactのSPAをS3をオリジンとしCloudFrontから静的配信し、SSRを採用しない。OpenNextおよびNext.js Server Runtimeも利用しない。

採用理由は、SSRの主な利点であるSEOと初期表示性能が社内アプリでは不要であり、静的配信が最も構成が単純なためである。

サーバーとの通信はRESTを基本とし、チャットの進行配信のみSSEを用いる。SSEを成立させるための配信経路の設定はarchitecture.mdに記載する。

## Consequences

メリット

- デプロイがS3への静的ファイル同期のみで完結する
- SSR用のサーバーランタイムを管理する必要がない
- オリジンがS3のみで完結し、実行環境の運用対象が増えない

デメリット・制約

- 初回アクセス時にJavaScriptバンドルの取得と実行が必要で、SSRより初期表示が遅くなる
- ページごとの動的なOGPなど、サーバー側でHTMLを生成する機能は実現できない

見直し条件

- 社外公開やSEO要件、ページごとの動的なHTML生成が必要になった場合はSSRを再検討する

## Alternatives

### Next.js + OpenNextによるSSR

Lambda上でSSRを動かせるため、サーバーレス方針とは両立できる。しかし、ビルドとデプロイの構成が複雑になり、LambdaでのSSR実行によるコールドスタートの影響も考慮する必要がある。SEO要件がない本システムでは複雑さに見合うメリットがないため不採用とした。

### Next.jsのstatic exportによるSSG

ビルド時にHTMLを生成するため、S3からの静的配信を保ったままSEOと初期表示性能を得られる。しかし本システムは全画面が認証必須で、表示内容はログインユーザーごとに異なり、ビルド時に確定するページが存在しない。SSGの利点が得られないままNext.jsへ寄せる構成コストだけが残るため不採用とした。
