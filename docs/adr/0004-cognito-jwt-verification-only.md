# ADR-0004: Cognito Hosted UI採用、バックエンドはJWT検証のみ

- Status: Accepted
- Date: 2026-07-18

## Context

移植元の実装はX-User-Idヘッダの値でユーザーを識別しており、認証の仕組みがない。ヘッダを書き換えれば誰にでもなりすませるため、社内利用であってもこのまま運用はできない。課題は、パスワード管理やトークン発行を自前で実装せずに、信頼できるユーザー識別をどう実現するかである。

## Decision

Cognito User PoolのHosted UIをAuthorization Code + PKCEフローで採用する。バックエンドのFastAPIはJWKSによるアクセストークンの検証のみを行い、user_idはJWTの`sub`クレームを利用する。パスワード管理とJWT発行は実装しない。

採用理由は、認証情報の保管と発行をマネージドサービスへ委譲でき、想定ユーザー数ではCognitoの無料枠内で運用できるためである。認証フローと画面遷移はarchitecture.mdの認証設計に、ユーザー登録・トークン保存・ライブラリ選定の詳細は[authorization.md](../authorization.md)に記載する。

## Consequences

メリット

- パスワード保管とトークン発行の実装および漏えいリスクをバックエンドから排除できる
- ユーザー識別が署名検証を通るため、ヘッダ偽装によるなりすましができない
- Cognitoの無料枠内に収まり、固定費が発生しない

デメリット・制約

- Hosted UIの画面デザインはカスタマイズの自由度が低い
- 認証仕様がCognitoに依存し、他基盤への移行コストが生じる

見直し条件

- 社外ユーザーへの提供やSAML / OIDCによるIdP連携が必要になった場合は、Cognitoへのフェデレーション追加を検討する

## Alternatives

### X-User-Idヘッダの継続利用

実装コストはゼロだが、なりすましを防げない。認証基盤としての要件を満たさないため不採用とした。

### 認証の自前実装

FastAPI側でパスワード保管とJWT発行を実装する方式である。要件に合わせた自由度は最も高いが、認証情報の保護、パスワードリセット、トークン失効などの実装と運用リスクをすべて自前で負うことになる。セキュリティ上の利点がないため不採用とした。

### Auth0などの外部IDaaS

機能とドキュメントは充実しており、無料プランでも本システムの想定ユーザー数は収容できる。しかしAWS外への依存が増え、IAMとは別にアカウント管理の系統を持つことになる。CognitoであればCDKとIAMで他のリソースと同じように管理でき、要件も満たせるため不採用とした。
