# ADR-0016: 推論の呼び出し経路をAmazon Bedrockへ統一する

- Status: Accepted
- Date: 2026-08-30

## Context

回答生成にOpenAI、埋め込みとリランクにCohereのAPIを直接呼んでいる。この構成には2つの課題がある。

- APIキーの管理が必要になる。SSM Parameter StoreのSecureStringで2本のキーを保管しているが、自動ローテーションの手段がなく、更新は手動運用となる
- 社内文書の本文が外部のSaaSへ出る。取込時の埋め込み、検索時のリランク、回答生成のいずれもチャンク本文をOpenAIまたはCohereへ送信している

一方で、Bedrockのモデル提供が広がり、Cohere Embed v4とCohere Rerank 3.5がap-northeast-1のオンデマンド推論で使えるようになった。ただしリランクはRerank 3.5までで、現在使っているrerank-v4.0-fastに相当するモデルはない。

## Decision

推論の呼び出し経路を全てBedrockへ統一する。呼び出し先のエンドポイントは他の4スタックと同じap-northeast-1とする。採用するモデルはarchitecture.md 7.2に示す。

APIキーは廃止する。SSM SecureStringの2パラメータとKMSによる復号をやめ、Lambdaの実行ロールにBedrockの呼び出し権限を与える。認可はIAMに一本化される。

4チェーンとも同じモデルで賄う。ただし回答生成と補助で設定は分けたまま残し、回答生成だけを差し替えられるようにする。クエリ生成と自己評価は構造化出力を使うため、補助側にはJSON Schemaの件数制約を守るモデルを選ぶ。この制約はモデルを差し替えても変わらない。

モデルを1つに寄せるのは、監視と設定の対象を増やさないためである。対抗馬としたgpt-oss-120bは、回答生成に限れば複数の処理を統合して説明する質問でより正確な回答を返した事例がある。しかし構造化出力の件数制約を守らず、6回試行して6回とも上限を超えたため補助には使えず、2モデル構成にしなければ採用できない。そのうえgpt-oss-120bのクォータはService Quotasに公開されておらず、上限の確認も引き上げ申請もできない。リランクの毎分3リクエストという天井を既に抱えている以上、上限を観測できないモデルを併用する負担の方が、1問で観測した品質差より重いと判断した。

埋め込みはモデルも出力次元も変わらないため、取込済みドキュメントの再取込は不要である。デプロイ済みのインデックスに対して実際に検索し、Cohereの直接APIで登録したベクトルがBedrock経由のクエリで正しくヒットすることを確認した。

採用理由は次の2点である。

- キーの保管とローテーションが不要になる。ADR-0008が制約として残していた手動運用の問題は、キーそのものがなくなることで解消する
- 文書の本文と検索クエリが第三者のSaaSへ渡らなくなる

データを処理するリージョンには要件を置かない。採用したモデルは結果としていずれも国内で処理されるが、これは選定の結果であって制約ではない。

## Consequences

メリット

- APIキーの保管とローテーションが不要になり、認可がIAMに一本化される
- 文書の本文と検索クエリがAWSの外へ出ない
- 認証情報の扱いがboto3に統一され、ingest-fnがhttpxでCohereのREST APIを直接呼ぶ実装がなくなる

デメリット・制約

- リランクがRerank 3.5へ後退する。第三者のベンチマークではRerank 4 Fastとの差が総合で54 ELO、ビジネス系のデータセットで約300 ELOと報告されており、社内文書という対象領域はこの差が出やすい側にあたる。自前では測定していない
- スループットがアカウントのクォータに縛られる。AWSの既定値はCohere Embed v4が毎分1,000リクエスト、Cohere Rerank 3.5が毎分250リクエストだが、現在のアカウントにはそれぞれ10と3が適用されている。1チャットはリランクを1回、埋め込みをクエリ数だけ呼び、最大1回の再試行でそれぞれ倍になるため、この水準では同時アクセスが重なると絞られる。取込側も同じ埋め込みのクォータを共有し、96チャンクずつ逐次に呼ぶため大きな文書1件でも超えうる
- 上記はBedrockの制約ではなくアカウントの状態である。適用値が既定値まで戻れば解消するが、Service Quotasからは引き上げを申請できない
- 選べるモデルがBedrockの提供状況とアカウントの開放状況に依存する。第一候補としたGPT-5.6 Lunaは、モデル契約を終えても全経路でaccess_deniedとなる。mantleエンドポイントにはクォータが割り当てられているため上限の問題ではなく、その手前で拒否されている。AWSへ問い合わせ中である
- 構造化出力はConverse APIのツール呼び出しを経由するため、OpenAIのStructured Outputsとは挙動が異なる

見直し条件

- GPT-5.6 Lunaがaccess_deniedを返さなくなった時点で、回答生成の品質を比較して差し替えを判断する。戻す場合はglobalの推論プロファイル経由となり、処理するリージョンが国内に限られなくなる
- BedrockがCohere Rerank 4へ対応した時点で乗り換える
- クォータの適用値が既定値まで戻ればスループットの制約は解消する。それまでにスロットリングが表面化した場合は、Multi Queryのクエリ数を減らす

APIキーの保管方式を定めたADR-0008は、対象となるキーが存在しなくなるため本ADRで置き換える。

## Alternatives

### リランクのみCohereのAPIを直接呼ぶ

Rerank 4 Fastの品質と、毎分3リクエストより高いレート上限を維持できる。

しかしCohereのキーが1本残るため、キー管理の廃止と本文をAWS内に留める狙いの両方が失われる。リランクは検索したチャンクの本文をそのまま送る処理であり、ここが残る限りデータの所在は説明できない。移行の目的を打ち消すため採用しない。

### 現状維持

移行の作業と、リランクの品質低下およびレート上限の低下を避けられる。

しかしキーの手動運用と本文の外部送信が残り、3つの課題のうち2つが解決しない。回答生成のモデルを差し替えれば費用の課題だけは解消するため、移行の主目的はあくまで前者2つである。
