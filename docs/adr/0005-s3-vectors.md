# ADR-0005: ベクトルDBにS3 Vectorsを採用

- Status: Accepted
- Date: 2026-07-18

## Context

移植元のRAG実装はRetrieverとしてChromaを利用しているが、Chromaは常駐プロセスと永続ストレージを前提としており、サーバーレス構成に載らない。固定費ゼロとVPC不使用の方針を守れるベクトル検索基盤の選定が課題である。

## Decision

Amazon S3 Vectorsを採用し、移植時にRetrieverをChromaから差し替える。

採用理由は、ストレージと検索リクエストの従量課金のみで固定費が発生せず、VPCも不要なためである。S3 Vectorsは2025年12月に一般提供が開始されており、東京リージョンで利用できる。Metadata設計と検索方針はarchitecture.mdのデータ設計に記載する。

インデックスは次元数1536、距離計算をコサイン類似度として作成する。Embeddingの生成にはCohere embed-v4.0を利用する。

## Consequences

メリット

- 固定費ゼロかつVPC不要でベクトル検索を運用できる
- クラスタやインデックスノードの管理が不要になる
- AWS内で完結し、アクセス制御をIAMへ統一できる

デメリット・制約

- インデックスの次元数、距離計算方式、Metadataのフィルタ可否は作成後に変更できない。Embeddingモデルを変更する場合はインデックスを作り直し、全ドキュメントを再取込する必要がある
- チャンク本文はフィルタ不可のMetadataとして保持するため、本文を条件にした絞り込みはできない。フィルタに使えるのは`documentId`のみである
- 検索機能は近傍検索とMetadataフィルタに限られ、ハイブリッド検索などの高度な機能はない

見直し条件

- 検索レイテンシまたは精度が要件を満たさなくなった場合は、OpenSearchなどへの移行を再検討する

## Alternatives

### Chromaの継続利用

移植コストは最小になる。ただしChromaには埋め込みモードとサーバーモードがあり、それぞれ別の理由で本構成に載らない。

埋め込みモードはメタデータをSQLite、インデックスをファイルとして永続化し、呼び出し元のプロセス内で動作する。Lambdaでは実行環境ごとにファイルシステムが独立するため、実行環境をまたいでデータを共有できない。共有するにはEFSが必要となりVPC不使用の方針に反する。加えて、複数の実行環境から同一のSQLiteへ同時に書き込む構成は整合性を保てない。

サーバーモードはアクセスが単一のサーバープロセスへ直列化されるため、同時実行による整合性の問題は生じない。しかしそのサーバーを常駐させるECSまたはEC2が必要となり、固定費が発生する。プライベートに配置するならVPCも必要になる。

いずれのモードもADR-0001の方針と両立しないため不採用とした。

### OpenSearch Serverless

検索機能は最も豊富だが、最低OCUに対する時間課金があり、利用がなくても月数万円規模の固定費が発生する。本システムの利用量では過剰なため不採用とした。

### Auroraとpgvector

SQLと組み合わせた柔軟な検索ができるが、Auroraの固定費とVPCが必要になる。不採用とした。

### Pineconeなどの外部ベクトルDB SaaS

無料枠はあるが、AWS外への依存とドキュメントデータの持ち出しが増える。S3 Vectorsで要件を満たせるため不採用とした。
