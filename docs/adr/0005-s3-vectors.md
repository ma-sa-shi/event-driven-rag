# ADR-0005: ベクトルDBにS3 Vectorsを採用

- Status: Accepted
- Date: 2026-07-18

## Context

移植元のRAG実装はRetrieverとしてChromaを利用している。Chromaを現在のサーバーレス構成へ載せるには、永続ストレージの共有または常駐サーバーが必要になる。固定費回避とVPC不使用の方針を守れるベクトル検索基盤の選定が課題である。

## Decision

Amazon S3 Vectorsを採用し、移植時にRetrieverをChromaから差し替える。

S3 Vectorsは固定費が発生せず、VPCも不要であるため、本システムのサーバーレス構成と固定費回避の方針に適合する。

インデックスは次元数1536、距離計算はコサインとする。Embeddingの生成にはCohere Embed v4.0を利用する。documentIdをfilterable metadataとし、チャンク本文は検索フィルタの対象としない。

## Consequences

メリット

- 固定費が発生せず、VPCも不要でベクトル検索を運用できる
- クラスタやインデックスノードの管理が不要になる
- AWS内で完結し、アクセス制御をIAMへ統一できる

デメリット・制約

- インデックスの次元数、距離計算方式、Metadataのフィルタ可否は作成後に変更できない。Embeddingモデルの変更によって次元数や距離計算方式が変わる場合は、インデックスを作り直し、全ドキュメントを再取込する必要がある。
- 本システムではチャンク本文をnon-filterable metadataとして保持するため、本文を条件にした絞り込みは行わない。フィルタに使用するmetadataはdocumentIdのみとする。
- 本構成では近傍検索とMetadataフィルタのみを利用し、ハイブリッド検索などの高度な検索機能は採用しない。

見直し条件

- 検索レイテンシまたは精度が要件を満たさなくなった場合は、OpenSearchなどへの移行を再検討する

## Alternatives

### Chromaの継続利用

移植コストは最小になる。ただしChromaには埋め込みモードとサーバーモードがあり、それぞれ別の理由で本構成に載らない。

埋め込みモードはメタデータをSQLite、インデックスをファイルとして永続化し、呼び出し元のプロセス内で動作する。Lambdaでは実行環境ごとにファイルシステムが独立するため、実行環境をまたいでデータを共有できない。共有するにはEFSが必要となりVPC不使用の方針に反する。加えて、複数の実行環境から同一のSQLiteへ同時に書き込む構成は整合性を保てない。

サーバーモードはアクセスが単一のサーバープロセスへ直列化されるため、同時実行による整合性の問題は生じない。しかしそのサーバーを常駐させるECSまたはEC2が必要となり、固定費が発生する。プライベートに配置するならVPCも必要になる。

いずれのモードも固定費回避とVPC不使用の方針と両立しないため不採用とした。

### OpenSearch Serverless

最低OCUの継続利用に伴う時間課金が発生し、アイドル時にも一定のコストが残るため不採用とした。

### Auroraとpgvector

SQLと組み合わせた柔軟な検索ができるが、Auroraの固定費が発生し、VPCも必要になるため不採用とした。

### Pineconeなどの外部ベクトルDB SaaS

無料枠はあるが、AWS外への依存とドキュメントデータの持ち出しが増える。S3 Vectorsで要件を満たせるため不採用とした。
