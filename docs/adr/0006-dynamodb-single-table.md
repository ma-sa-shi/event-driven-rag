# ADR-0006: チャット永続化をDynamoDBシングルテーブルへ差し替え

- Status: Accepted
- Date: 2026-07-18
- Updated: 2026-07-23

## Context

移植元はMySQLのchat_historiesテーブルとchat_detailsテーブルでチャットを永続化している。本構成でRDBを使うにはAuroraなどのマネージドRDBが必要となり、固定費ゼロとVPC不使用の方針に反する。ユーザー、ドキュメント、チャットの永続化先の選定が課題である。

## Decision

DynamoDBのシングルテーブル設計へ差し替え、全エンティティを1つのテーブルで管理する。

採用理由は、オンデマンドキャパシティによる従量課金で固定費が発生しないこと、VPCが不要なこと、そして本システムのアクセスパターンが一覧取得と詳細取得に限られており、キー設計とGSIで十分表現できることである。キー設計の詳細はarchitecture.mdのデータ設計に記載する。

ドキュメントとチャットのIDはULIDで採番し、GSI1のソートキーにはcreatedAtではなくIDそのものを利用する。チャット詳細の取得や閲覧用署名付きURLの発行は、所有者のユーザーIDを持たずIDだけでアイテムを特定する必要がある。ソートキーをIDにすると、横断一覧と同じGSIのQueryでID単独の取得を実現でき、追加のインデックスが不要になる。ULIDは先頭にミリ秒精度のタイムスタンプを持ち辞書順が作成時刻順となるため、一覧の並びも維持される。

## Consequences

メリット

- 固定費が発生せず、負荷に応じて自動でスケールする
- テーブルが1つのため、バックアップや監視の設定対象が最小になる

デメリット・制約

- アクセスパターンを事前に設計する必要があり、後からの変更にはキーやGSIの再設計が伴う
- SQLのようなアドホックな集計・検索はできない
- GSI1PKが`CHAT`と`DOC`の固定値であるため、GSI1上のパーティションが分散しない。DynamoDBのパーティションには書き込みと読み込みのスループット上限があり、ADR-0001で想定する月400件から600件の規模では上限に対して十分な余裕があるが、書き込み量が桁違いに増える場合はGSI1PKへ日付などを含めて分散させる必要がある
## Alternatives

### Aurora Serverless v2とMySQLスキーマの継続

移植元のスキーマをほぼそのまま利用でき、SQLの柔軟性も維持できる。しかしVPC内にしか配置できず、Lambdaからの接続経路に固定費が発生する。詳細はADR-0001のAlternativesに記載する。本システムのアクセスパターンはSQLの柔軟性を必要としないため不採用とした。

### DynamoDBマルチテーブル

エンティティごとにテーブルを分ける方式で、構造は直感的になる。しかし本システムの規模ではテーブルを分ける利点が薄く、横断取得のためのインデックス管理が分散する。シングルテーブルで十分表現できるため不採用とした。
