## このドキュメントの目的

ADRは設計判断を記録する文書である。

「何を採用したか」ではなく、「なぜ採用したか」を記録することを目的とする。

## ドキュメント構成

次の構成を基本とする。

1. タイトル
2. ステータス
3. 日付
4. Context
5. Decision
6. Consequences
7. Alternatives（必要な場合）

## 文体ルール

- 結論を最初に書く
- 比較検討を客観的に記述する
- トレードオフを隠さない
- 括弧による補足説明は原則禁止
- 箇条書きを適切に利用する
- 用語を統一する
- 曖昧な表現を避ける

## 記述ルール

必ず以下を説明する。

- 何が課題だったか
- どの選択肢を比較したか
- 採用した選択肢
- 採用理由
- 採用しなかった選択肢と理由
- 採用によるメリット
- デメリット・制約
- 将来的な見直し条件（必要に応じて）

### 他文書の参照

前提はシステムの仕様として断定して書き、どの文書に書いてあるかは書かない。

- 「architecture.mdは〜と定めている」「ADR-0004により〜」のような出典の明示をしない。前提そのものを事実として述べる
- 文書名やADR番号を出すのは、その決定を覆す・置き換える・範囲を変えるときと、詳細の参照先を示すときに限る
- 参照先の記述を書き写さない
- 一度示した前提を、同じADRの中で再説明しない

## 完成前チェック

- [ ] Contextが十分に説明されている
- [ ] Decisionが明確である
- [ ] Alternativesが整理されている
- [ ] Consequencesにメリットとデメリットが記載されている
- [ ] トレードオフが説明されている
- [ ] 読者が判断の背景を理解できる
