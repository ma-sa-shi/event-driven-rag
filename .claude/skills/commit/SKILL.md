## Commit messages

コミットメッセージは、変更内容と主要な意図を簡潔に記録する。
実装上の細部や検証過程をすべて説明する「実装メモ」にはしない。

形式:

- 件名・本文とも英語で書く
- 件名は `type(scope): 要約` とし、命令形で72文字以内に収める
- typeは `feat` / `fix` / `docs` / `refactor` / `test` / `build` / `ci` / `chore`
- scopeは `frontend` / `backend` / `cdk` / `ci` / `auth` / `adr`。複数はカンマで繋ぎ、全体に及ぶ場合は省く
- `Co-Authored-By` などのトレーラーは付けない

原則:

- subjectは「何を変更したか」を短く表す
- bodyは必要な場合だけ書く
- bodyを書くときは、1文で「何が変わったか」を述べ、続けて変更ごとに1つの箇条書きを置く
- bodyでは「なぜ変更したか」「重要な設計判断」を補足する
- コード内で自明な設定理由や細かな実装手順は書きすぎない
- バージョン固有の細かな仕様や調査メモは、必要ならPR本文やコードコメントへ置く
- 1コミットで複数の論点を説明しすぎない

## Pull request descriptions

PR本文は、レビューに必要な判断材料を提供する。
差分を読めば分かることは書かず、差分からは読み取れないことだけを書く。

形式:

- タイトルは英語、本文は日本語で書く
- タイトルは命令形で、`type(scope):` のプレフィックスは付けない
- 本文は次の3つの `###` 見出しで構成する。見出しの追加・削除・改名はしない
- 末尾に区切り線 `---` を置き、含まれるコミットの件名を並べ、`Closes #<番号>` で締める

見出し:

1. 実装内容
2. 検証結果
3. 注意事項

原則:

- 本文には差分が語らないことを書く。なぜ必要か、何が壊れうるか、何を確認したか
- 実装内容は、変更したモジュールごとに「何がどう変わったか」を1行ずつ書いて止める。差分はレビュアーが読むため、再説明しない
- そこへ至った調査や試行錯誤の経緯は本文へ書かない。必要ならPRのコメントかIssueへ置く
- レビューで判断が必要な設計上の選択と、その代替案を却下した理由は明示する
- 検証結果では実行したコマンドと確認した事実を書き、未実施の確認は注意事項へ回す
- テストは件数ではなく、何を保証するテストなのかを書く
- 注意事項では運用手順の変更、レビューで誤解されやすい点、積み残しを挙げる
- コミットメッセージと同じ内容を繰り返さない

分量:

- 実装内容は変更モジュール数と同程度の行数に収める
- 3つの見出し合計で60行を超えたら、差分の再説明か調査経緯が混ざっていないか疑う
