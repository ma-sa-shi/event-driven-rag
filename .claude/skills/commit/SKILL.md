## Commit messages

コミットメッセージは、変更内容と主要な意図を簡潔に記録する。
実装上の細部や検証過程をすべて説明する「実装メモ」にはしない。

形式:

- 件名・本文とも英語で書く
- 件名は `type(scope): 要約` とし、命令形で72文字以内に収める
- typeは `feat` / `fix` / `docs` / `refactor` / `test` / `build` / `ci` / `chore`
- scopeは `frontend` / `backend` / `cdk` / `ci` / `auth` / `adr`。複数はカンマで繋ぎ、全体に及ぶ場合は省く
- `Co-Authored-By` などのトレーラーは付けない

原則:

- subjectは「何を変更したか」を短く表す
- bodyは必要な場合だけ「なぜ変更したか」「重要な設計判断」を補足する
- コード内で自明な設定理由や細かな実装手順は書きすぎない
- バージョン固有の細かな仕様や調査メモは、必要ならPR本文やコードコメントへ置く
- 1コミットで複数の論点を説明しすぎない

## Pull request descriptions

PR本文は、変更の全体像とレビューに必要な判断材料を説明する。
コミットメッセージより詳細に書いてよいが、実装の逐次的な作業記録にはしない。

形式:

- タイトルは英語、本文は日本語で書く
- タイトルは命令形で、`type(scope):` のプレフィックスは付けない
- 本文は次の3つの `###` 見出しで構成する。見出しの追加・削除・改名はしない
- 末尾に区切り線 `---` を置き、含まれるコミットの件名を並べ、`Closes #<番号>` で締める

見出し:

1. 実装内容
2. 検証結果
3. 注意事項

原則:

- 実装内容では「何をしたか」に加え、変更のきっかけと「なぜその方針にしたか」を必要な範囲で説明する
- 検証結果では実行したコマンドや確認した事実を書き、未実施の確認は注意事項へ回す
- 注意事項では運用手順の変更、レビューで誤解されやすい点、積み残しを挙げる
- レビューで判断が必要な設計上の選択は明示する
- テストの件数だけでなく、何を保証するテストなのかを説明する
- テストの有効性を実装破壊などで検証した場合、その結果は価値が高いため記載してよい
- 低レベルな実装詳細は、レビューに不要なら省略する
- 既存の警告や`npm audit`など、レビューで誤解されやすい事項は明示する
- コミットメッセージと同じ内容を繰り返さず、PRでは変更全体を俯瞰できる情報を優先する
